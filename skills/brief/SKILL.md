# 내 작업 설명 연습

목표: 제출 전 15분 안에, 사용자가 "왜 이렇게 했는지 / AI와 어떻게 일했는지 / 실제로 어떻게 동작하는지"를 근거와 함께 자기 말로 말할 수 있게 한다.

두 가지 모드가 있다.
- **정리** (기본, `$brief`): 작업 정리 + 설명 연습 질문과 답변 뼈대를 한 번에 보여준다.
- **연습** (`$brief 연습`): 질문을 하나씩 내고, 사용자가 먼저 답하면 점검해 준다.

## 공통 규칙
- 파일을 만들거나 고치지 않는다. 출력은 터미널에만 한다 (제출물에 섞이지 않게). 그래서 구현 중인 다른 Codex 창과 동시에 써도 된다.
- 근거가 있는 내용만 쓴다: 코드, `git log`, 계획 문서(결정 기록·AI 협업 기록·실무자 확인 내용), README, 테스트 결과. 기억에 의존해 지어내지 않는다.
- 근거는 항상 짚어 준다: `파일:함수`, 커밋 해시와 메시지, 결정 번호(D3), 숫자(테스트 수, 데이터 건수).
- 전문용어는 처음 나올 때 쉬운 말로 한 번 풀어 준다.
- 계획 문서의 내용과 실제 코드가 다르면 그 차이를 먼저 알려 준다. 질문의 전제가 실제 구현과 다를 수 있다.

## 근거 모으기 (두 모드 공통, 출력은 짧게)
1. `git log --oneline --reverse | head -60`
2. `git diff --stat $(git rev-list --max-parents=0 HEAD | head -1) HEAD | tail -25`
3. 계획 문서 전체, README의 요구사항·제출물 부분
4. 진입점과 핵심 파일만 읽는다: 서버 진입점, 라우트(API) 정의, 핵심 계산 로직, 화면별 주요 스크립트. 전체 코드를 다 읽지 않는다.
5. 테스트 목록과 마지막 실행 결과 (`pytest -q` / `npm test` 등, 출력은 요약만)

## 정리 모드 출력 형식

```
# 한 줄 요약
<누구를 위해, 무엇을, 어떻게>

# 화면별 사용 흐름
- <역할 A 화면>: 사용자가 ... 하면 → ... 가 보인다
- <역할 B 화면>: ...

# 요청 흐름 추적 (핵심 기능 1~2개)
<기능 이름>
1. 브라우저: <어떤 버튼/입력> → <프론트 파일:함수> 가 이벤트 처리
2. 프론트 → 서버: <HTTP 메서드 경로>, 보내는 데이터 <형식>
3. 서버: <라우트 파일:함수> → 입력 검증 <무엇을 막는지>
4. 처리: <핵심 로직 파일:함수> — <무엇을 계산/판단하는지 한두 줄>
5. 데이터: <CSV/메모리/파일 중 어디서 읽고 어디에 쓰는지>
6. 응답 → 화면: <응답 형식> → <프론트 함수> 가 화면을 다시 그림
오류일 때: <어떤 입력이면 어떤 응답/메시지>

# 구조 (핵심 3~6개 파일)
- <파일>: <역할 한 줄>

# 핵심 결정 (선택 → 이유 → 버린 대안)
1. D<n> ...

# AI 협업에서 막힌 점과 해결
1. <상황> → <무엇이 문제였나> → <내가 어떻게 판단·해결했나> → <결과>

# 검증한 것 / 남은 한계
- 검증: ...
- 한계 → 시간이 더 있었다면: ...

# 설명 연습 질문 (10개 안팎)
아래 유형에서 이 작업에 실제로 해당하는 것만, 결정이 많았던 부분 위주로 고른다.
각 질문마다:
Q<n>. <질문>
  답변 뼈대: 결론 → 이유 → 근거(파일·함수·커밋·숫자) → 한계·대안
  꼭 말할 단어: <3~5개>
```

### 질문 유형
1. **선택의 이유**: "왜 A 방식이 아니라 B 방식으로 했나요?" — 기술 스택, 데이터 저장 방식, 핵심 계산 방법, 화면 분리 방식, 범위를 줄인 결정
2. **AI 협업**: "AI를 쓰면서 가장 큰 어려움은 무엇이었고 어떻게 해결했나요?", "AI가 만든 결과가 맞는지 어떻게 확인했나요?", "AI 제안을 받아들이지 않은 적이 있나요?"
3. **동작 흐름**: "사용자가 <버튼>을 누르면 프론트와 서버에서 어떤 일이 순서대로 일어나나요?", "사용자 유형별 화면이 여러 개라면, 같은 데이터를 화면마다 어떻게 다르게 보여주나요?"
4. **데이터 처리**: "입력 파일(CSV 등)을 어떻게 읽고, 잘못된 값이나 빠진 값은 어떻게 처리했나요?"
5. **요구사항과 실무자**: "README의 어떤 조건이 애매했고, 실무자에게 무엇을 물어 어떻게 반영했나요?"
6. **검증과 한계**: "어떻게 검증했나요?", "어떤 상황에서 틀린 결과가 나올 수 있나요?", "실제 서비스라면 무엇을 바꾸겠어요?"

## 연습 모드 진행
1. 근거를 모은 뒤, 위 질문 유형에서 이 작업에 맞는 질문을 6~8개 정한다. 질문 목록은 미리 보여주지 않는다.
2. 질문을 **하나만** 낸다. 답변 뼈대는 보여주지 않고, 사용자의 답을 기다린다.
3. 사용자가 답하면 짧게 점검한다:
   - 맞게 말한 부분 (1줄)
   - 빠졌거나 틀린 부분: 근거와 함께 (예: "실제로는 `routes.py:assign`에서 검증한다")
   - 5분 안에 쓸 수 있는 3~4문장 구조 제안 (결론 → 이유 → 근거 → 한계). 사용자가 자기 말로 다시 쓸 수 있게 문장 통째로가 아니라 순서와 키워드 위주로.
4. "다음"이라고 하면 다음 질문으로 넘어간다. "다시"라고 하면 같은 질문에 다시 답하게 한다.
5. 끝나면 다시 읽어 볼 곳을 3개 이내로 알려 준다 (`파일:함수`, 결정 번호).
