# 결정 기록

## 순서

1. PLAN.md(또는 README가 지정한 계획 문서)를 연다. 없으면 `$start`의 뼈대로 만든다.
2. 결정이면 "결정 기록"에 D 형식으로, AI와 일하다 막힌 일이면 "AI 협업 기록"에 A 형식으로 추가한다. 번호는 이어서 붙인다. 섹션이 없으면 만든다.
3. 관련 요구사항 체크박스나 "검증 결과", "남은 한계" 섹션도 함께 갱신한다.
4. 사용자에게 추가한 항목을 그대로 보여준다.

## 형식

```markdown
### D<번호>. <결정 제목>
- 선택: <무엇을 골랐는지>
- 대안: <고려했지만 버린 것> (없으면 생략)
- 이유: <왜 — 요구사항, 시간, 데이터 크기 등 구체적 근거>
- 검증: <어떻게 확인했는지와 결과 — 명령어, 테스트 수, 화면 확인>
- 한계: <아직 안 되는 것, 실서비스라면 바꿀 점>
- 바로잡은 점: <AI 제안을 사용자가 고치거나 거절한 내용> (없으면 생략)
```

## AI 협업 기록 형식

```markdown
### A<번호>. <한 줄 제목>
- 상황: <무엇을 시켰나>
- 문제: <AI가 무엇을 잘못했나 / 어디서 막혔나 — 요구사항 오해, 틀린 코드, 같은 실패 반복, 느린 응답 등>
- 내 조치: <어떻게 알아챘고 무엇을 판단·지시했나 — 테스트, 화면 확인, 실무자 질문, 범위 조정>
- 결과: <해결 여부와 근거 — 테스트 수, 커밋>
```

예: `### A2. 날짜 필터 경계 오류` / 문제: README는 "마감일 당일 포함"인데 AI가 당일을 빼고 구현 / 내 조치: 경계값 테스트로 차이를 확인하고 기준을 다시 지시 / 결과: test_due_date 3개 통과, 커밋 a1b2c3d

## 예시

```markdown
### D2. 데이터 저장 방식
- 선택: JSON 파일 저장
- 대안: SQLite
- 이유: 데이터가 100건 이하이고 3시간 안에 끝내야 해서 DB 설정 비용이 큼
- 검증: 저장 → 서버 재시작 → 조회 시 데이터 유지 확인 (test_persist 통과)
- 한계: 동시 쓰기 시 충돌 가능 → 실서비스면 SQLite로 교체
```

## 원칙
- 짧게. 항목당 한 줄.
- 실제로 한 검증만 적는다. 아직 검증 안 했으면 "검증: 미실시"라고 적는다.
- AI가 제안했다가 사용자가 거절·수정한 내용도 이유와 함께 남긴다. 나중에 설명할 거리가 된다.
